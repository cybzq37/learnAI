# 智能体

**LLM与Agent的区别**：LLM负责“思考”，根据输入的内容去推测输出的内容，问答模式；Agent 则是负责“行动”，完成目标，给它一个目标，它会自己去规划、调用工具、执行，直到完成目标。


**LLM** 本质上是一个"预测下一个词"的概率模型，通过海量数据训练而成，拥有知识、推理与语言理解能力，却**没有主动行为**——你不输入，它就不输出。

**Agent** 则是动态系统：以 LLM 为核心控制器，额外封装了规划、记忆、工具调用与行动执行能力，能自主完成复杂任务。二者差异，正是「会聊天」与「能办事」的差异。

LLM发展历史：

## 阶段一：提示词工程（Prompt Engineering）

这一阶段主要研究“怎么通过语言告诉 LLM 应该做什么”，例如：

```
Role
Task
Context
Examples
Constraints
Output Format
```

典型技术如：Zero-shot/Few-shot、CoT、Prompt Template、System / Developer Instructions、Structured Output

模型本身基本不变，主要优化：

```
User
 ↓
Prompt
 ↓
LLM
 ↓
Answer
```



## 阶段二：上下文工程（Context / Input Engineering）

这一阶段主要是围绕输入侧进行增强，比如上下文工程、RAG等。如果说Prompt = 很多模板 + 变量 + 组装，那么 到了 Context Engineering，可以进一步变成：Prompt + Context + Tools + Schema → LLM

```
User Question
      +
Conversation History
      +
RAG Documents
      +
Database Data
      +
User Profile
      +
External Information
      ↓
     LLM
```

上下文（Context）是指 **某一次推理中喂给模型的所有信息**，动态地收集、筛选、组织、压缩、排序上下文，然后交给 LLM。

包含内容：

- 用户输入
- 对话历史
- RAG检索
- 用户画像
- 数据库数据
- API返回结果
- memory
- 当前任务状态
- 多模态信息

核心技术：

- Conversation Context （哪些历史需要保留？哪些可以删除？哪些需要总结？）
- RAG （用户问题 -> Embedding / Search -> 找到最相关的 5 个文档 -> 组织 Context）
- Context Compression


它不只是提示词——后者只是其中「用户主动书写指令」的部分；一个完整上下文还包括系统指令、多轮对话历史、检索到的外部资料、工具执行结果、当前任务状态、中间产物、安全约束等。

上下文工程（Context Engineering）要解决的核心矛盾是：**窗口有限，但信息很多。** 它的目标，是在有限的上下文中决定「放什么、不放什么、按什么顺序放」，让模型在正确时机看到正确信息。它与提示词工程的分工在于：提示词工程优化的是「把指令写得更好」，上下文工程优化的是「**整个输入窗口怎么组织**」，范围更大。

**两个绕不开的硬约束**

1. **上下文窗口有上限**。超过窗口的内容会被直接截断（通常掐掉最中间或最旧的部分），信息无声无息地丢失。
2. **模型的注意力并非均匀分布**。研究（"Lost in the Middle"）发现：模型对**开头和结尾**记忆最好，对**夹在中间**的内容最易遗忘。当上下文塞得太满，模型会「前文失忆、自相矛盾、无视最初规则」——常被直观称为「上下文腐化」，本质是**注意力被稀释 + 长距离信息衰减**。

**上下文工程的四大手段**

- **检索 / 召回（Retrieval）**：**按需**取出与当前任务最相关的部分，而不是全塞进去。这是 RAG 的用武之地；想提升召回质量，可用多查询扩展（MQE）、假设文档嵌入（HyDE）、两路召回 + 精排（Rerank）等。
- **压缩（Compression）**：把超出窗口的内容做**摘要提炼**，用一句话总结代替大段原文，或把历史对话折叠成"纪要"。
- **截断 / 滑动窗口（Truncation / Sliding Window）**：对话无限增长时按优先级取舍——**系统指令、安全约束、当前任务必须保留**，最早/最旧的历史优先丢弃或降级为摘要。
- **组装 / 优先级排序（Assembly / Prioritization）**：利用「开头和结尾最敏感」的特性，把关键内容（任务指令、安全规则）放在开头或结尾，历史资料居中。

**渐进式披露（Progressive Disclosure）**

还有一个思路是「能不塞就不塞」：先只给模型看每个能力的「目录/摘要」，等它真的判断用到某能力时，再把详细说明、参数定义、使用示例**按需加载**进来（工具 schema 的惰性加载、Agent Skills 的按需引用都属于这类）。它点破了一个关键——上下文优化的本质是「**按需给、分层给、在正确的时机给**」，每次都要先规划好这个窗口的 token 预算怎么花。

**RAG 系统**

RAG（Retrieval-Augmented Generation，检索增强生成）是一种「**先检索、再生成**」的范式：回答前先从外部知识库检索相关资料，再注入上下文让模型据此作答。它让静态训练的模型能对**私有、实时、长尾**的知识给出基于事实的回答，也是缓解幻觉最重要的工程手段之一。

经典流程（Naive RAG）：三阶段

- **索引（Indexing）**：线下把文档**切块（Chunking）→ 用嵌入模型向量化 → 写入向量数据库**。切块粒度（chunk size / overlap）直接影响检索质量——太大噪声多，太小上下文割裂。
- **检索（Retrieval）**：把用户问题同样向量化，做**相似度检索**（余弦相似度、点积、L2），取最相近的 Top-K 块作证据，常叠加**混合检索**（BM25 关键词 + 向量语义）。
- **生成（Generation）**：把「Top-K 块 + 用户问题 + 系统指令」拼进 Prompt 交给 LLM 生成，并要求**引用出处**。若召回不足，检索后还要做 **Rerank（精排）** 与**上下文压缩**。

演进路线：从 Naive 到 Modular

- **Naive RAG**：三阶段直连，实现简单，但检索容易"命中却不相关"。
- **Advanced RAG**：检索**前/中/后**都优化——前（改写/扩展查询，如 MQE、HyDE）、中（混合检索）、后（Rerank + 上下文压缩）。
- **Modular RAG**：把 RAG 拆成可自由组合的模块（重写器、检索器、路由、融合器），按任务定制流水线。

RAG 质量的评估

- **检索侧**：召回率（Recall）、精确率（Precision）、排序质量（MRR / NDCG）、TopK 命中率。
- **生成侧**：答案正确率、**引用可溯源性**（结论能否对应到某段原文）、幻觉率。

局限与破局方向

- **依赖检索质量/能力**：切分不合理、领域偏差、复杂聚合/多跳推理都可能导致"召回不相关"。
- **知识冲突**：检索内容与模型参数知识矛盾时，需要"信检索"的取舍。
- 对应方向：**GraphRAG**（知识图谱增强多跳推理）、上下文压缩/摘要、路由（只对需要检索的问题走 RAG）等。

一句话总结：**RAG 就是上文「上下文工程」里"检索/召回"环节的成熟落地实现**——把「外部知识」主动送进有限的窗口。

> 至此，LLM 已经「说得更准」了，但它依然「只说不做」。真正的拐点，是让模型能**调用工具改变世界**——也就是 Agent 的起点。



## 阶段三：Action / Tool Use

这一阶段 LLM 具有了 Tool Calling / Function Calling 的能力。

```
User
 ↓
LLM
 ↓
决定调用什么工具
 ↓
Tool
 ↓
返回结果
 ↓
LLM
 ↓
Answer
```


要让 Agent 真正「能做事」，第一步是让模型学会调用外部工具，这个能力通常被称为 **Function Calling / Tool Calling**，并发展出了MCP。

**本质**：模型并不直接执行外部函数，而是输出一个结构化的「工具调用意图」（函数名 + 参数），由**应用程序**去真正执行，再把执行结果作为 `tool` 角色消息回传给模型。它解决了"把模型的自由文本决策，变成可被程序可靠执行的调用"这一关键问题。

**实现原理：**
- **定义函数**：用 JSON Schema 描述每个工具的名字、参数与用途。
- **模型判断**：模型根据用户请求和工具列表，决定是否调用、调用哪个、传什么参数。
- **执行函数**：应用程序在受控环境内真正执行该函数。
- **生成回答**：把工具返回值作为新的一轮消息喂回模型，模型据此输出最终答案。

**一次工具调用的消息交互（OpenAI 风格）：**

```json
{
  "messages": [
    { "role": "user", "content": "北京天气如何？" },
    { "role": "assistant", "content": null, "tool_calls": [
        { "function": { "name": "get_weather", "arguments": "{\"city\":\"北京\"}" } }
    ]},
    { "role": "tool", "tool_call_id": "...", "content": "晴，25℃" },
    { "role": "assistant", "content": "北京今天晴，25℃。" }
  ]
}
```

**关键点：**
- 模型要判断三件事：**何时调用**（是否该调）、**调用哪个**、**传什么参数**。
- 工具列表阶段就要给出准确的 schema，否则易出现"幻觉工具调用"。
- 多家厂商实现并不相同：有的是把函数描述放入 system 提示，有的是独立的 `tool` 字段和 schema（OpenAI / Anthropic 风格），但都收敛到"结构化调用意图 + 结果回填"这一模式。


工具接入越来越多样，「每个模型对接 N 个工具就要写 N 套集成」的碎片化问题凸显，于是协议化的连接方式应运而生。

**MCP（Model Context Protocol，模型上下文协议）**由 Anthropic 于 2024 年开源，是一项**开放的标准化协议**，用于统一 LLM 应用与外部数据源、工具之间的连接方式，常被比作「AI 应用的 USB 接口」。

- **三层架构**：Host（宿主，如 Claude Desktop、IDE）、MCP Client（内置在 Host 中的协议客户端）、MCP Server（暴露能力的服务端）。一个 Host 可连接多个 Server。
- **原语（Primitives）**：
  - `Tools`：会改变外部世界的可执行操作（发邮件、写数据库），由模型决定调用。
  - `Resources`：只读数据源（文件、数据库查询结果），供注入上下文。
  - `Prompts`：预定义的提示词模板（代码审查模板），复用交互流程。
- **传输方式**：采用 JSON-RPC 2.0 消息；传输层支持 stdio（本地进程）与 Streamable HTTP（原 HTTP+SSE，远程服务）。
- **调用流程（Tool）**：Client 向 Server 服务发现/工具列表 → 模型决定调用哪个 → Client 执行调用 → Server 返回结果 → 模型据此生成回答。
- **典型操作（Resources/Prompts）**：`resources/list`、`resources/read`、`prompts/list`、`prompts/get` 等。

**接入与渠道网关**

负责统一接入不同前端渠道和外部系统。

- 渠道适配器：Web Chat、OpenAPI、企业微信/钉钉/飞书、Slack/Teams、邮件、语音等。
- 协议标准化：将不同渠道的请求转换为统一的内部消息格式。
- 流式输出支持：支持 SSE、WebSocket 等流式响应。
- 限流与配额：按租户、用户、渠道进行 QPS 和并发控制。
- 接入安全：TLS、签名校验、防重放、IP 白名单等。

**身份认证与权限管理**

企业 Agent 必须做到“谁能问什么、谁能调什么、谁能看什么”。

- 身份认证：对接企业 SSO/OIDC/SAML、LDAP、AD。
- RBAC/ABAC：基于角色的访问控制，细粒度到工具、知识库、数据范围。
- 租户隔离：多租户数据、配置、模型配额、知识库完全隔离。
- 数据权限：例如销售 Agent 只能查自己负责的客户数据，需要与数据平台权限打通。
- 工具级授权：每个工具调用前进行二次鉴权。


**会话与状态管理**

企业任务往往不是一次问答，而是多步、长时、可中断的流程。

- 会话持久化：保存对话历史、任务状态、中间结果。
- 断点恢复：任务中断后可恢复到最近一致状态。
- 幂等控制：同一工具调用重复执行不应产生副作用。
- 并发与锁：同一会话/任务的并发操作控制。
- 超时与过期：会话超时回收，长期任务状态过期策略。

**上下文与记忆管理**

Agent 需要比单次对话更长的记忆能力。

- 短期记忆：当前对话窗口内的上下文管理、压缩、滑窗。  
- 长期记忆：用户偏好、历史任务、事实性知识，存入向量库或知识图谱。  
- 分层记忆：  
  - 用户级：个人偏好、常用指令。  
  - 会话级：当前任务相关实体。  
  - 组织级：企业知识、流程规范。  
- 记忆检索策略：基于相关性、时间衰减、重要性加权。  
- 遗忘与更新机制：过时信息自动失效或覆盖。  

**模型服务网关**

统一管理所有模型调用，屏蔽底层差异。

- 多模型接入：GPT、Claude、Gemini、开源模型、私有化模型。
- 智能路由：根据任务类型、成本、延迟、效果路由到不同模型。
- 缓存与去重：相同/相似请求缓存结果，降低成本。
- 降级与容灾：主模型不可用时自动切换备用模型。
- 成本计量：按 token、调用次数、租户统计成本。
- 模型输出后处理：统一格式化、安全过滤、引用溯源。

**推理与规划引擎**

这是 Agent 的“大脑”，决定如何理解目标、分解任务、调用工具。常见的认知架构模式：

- ReAct：思考-行动-观察循环，适合简单任务。
- Plan-and-Execute：先规划再执行，适合多步骤任务。
- 状态机/工作流：明确步骤和分支，适合企业固定流程。
- 多 Agent 协作：主 Agent 拆解任务，子 Agent 分别执行。
- 反思与自我修正：执行失败后自动重试、修正计划。

企业级要求：
- 规划结果可解释、可记录。
- 支持人工确认后执行。
- 可设置最大步数、超时时间、失败策略。

**工具/插件系统**

Agent 的能力边界由工具决定，工具系统必须标准化、可治理。

- 工具注册中心：统一注册工具 schema、描述、参数、权限。
- 工具协议：推荐采用或兼容 MCP、OpenAPI Function Calling 等标准。
- 工具执行沙箱：代码执行、SQL 查询等高风险操作必须沙箱化。
- 超时与重试：每个工具可配置超时、重试次数、退避策略。
- 工具调用日志：记录输入、输出、耗时、状态，用于审计和调试。
- 工具市场/版本管理：工具独立版本发布，支持回滚。
- 工具鉴权：调用前检查调用方是否有权限。

**知识库与RAG模块**

企业 Agent 通常需要基于内部知识回答。

- 多源数据接入：文档、表格、数据库、Wiki、工单系统。
- 文档解析与切片：PDF、Word、Markdown、图片 OCR、表格结构化。
- 索引与检索：向量检索、关键词检索、混合检索、重排序。
- 引用溯源：回答必须注明来源，支持跳转原文。
- 知识权限：检索结果必须经过数据权限过滤。
- 知识更新：增量更新、全量重建、版本管理。
- 知识质量评估：检索命中率、答案准确率监控。

**工作流编排引擎**

很多企业场景需要确定性流程，不能完全依赖模型自由发挥。

- 可视化/DSL 定义流程：节点、条件、循环、并行、子流程。
- 人工审批节点：关键操作需人工确认。
- 定时/事件触发：支持 cron、消息队列、Webhook。
- 状态持久化：流程状态落库，支持恢复。
- 版本管理：流程定义版本化，可回滚。

**安全与合规模块**

企业级必须内建安全能力。

- 提示词注入防护：检测并阻断恶意指令。
- 敏感数据识别与脱敏：对输入输出中的手机号、身份证、密钥等脱敏。
- 输出过滤：违规内容、幻觉内容、竞品信息过滤。
- 审计日志：谁在什么时间调用了什么工具，输入输出摘要，操作结果。
- 数据驻留与合规：数据不出境、GDPR、等保等要求。
- 模型安全：防止越狱、数据泄露训练。

**可观测性模块**

没有可观测性就无法上线企业级 Agent。

- 全链路追踪：每次请求的完整 trace，包括模型调用、工具调用、知识检索。
- 指标监控：延迟、成功率、token 消耗、工具调用成功率、用户满意度。
- 日志聚合：结构化日志，便于检索和分析。
- 告警：异常率、成本突增、模型不可用等自动告警。
- 调试回放：可重放某次会话，复现问题。
- 成本看板：按租户、应用、模型维度统计成本。

**评估与评测模块**

持续验证 Agent 效果，避免上线后质量不可控。

- 离线评测：准备标注数据集，自动跑分。
- 在线评测：抽样真实会话进行评分。
- LLM-as-Judge：用模型自动评估回答质量。
- 指标：准确性、相关性、工具调用准确率、任务完成率、用户满意度。
- 回归测试：提示词、模型、工具更新后自动跑回归。
- A/B 测试：灰度对比新旧版本效果。

**人机协同模块**

企业场景中完全自主风险高，需要人类参与。

- 人工审批：关键操作（发邮件、付款、删除数据）需人工确认。
- 转人工：Agent 无法处理或用户要求时，无缝转接人工。
- 任务确认：执行前向用户确认计划。
- 反馈闭环：用户可点赞/点踩、提交纠正，用于优化。

**配置与发布管理**

企业级 Agent 需要像软件一样管理版本和发布。

- 提示词版本管理：Git 化管理，支持 diff、回滚。
- 工具/知识库版本：版本绑定，确保可复现。
- 灰度发布：按用户/租户百分比逐步放量。
- 多环境：开发、测试、预发、生产环境隔离。
- 配置中心：动态配置，无需重启。

**运营管理后台**

面向运营和业务管理者的控制台。

- 租户管理：开通、禁用、配额管理。
- 应用管理：创建多个 Agent 应用，绑定不同模型、工具、知识库。
- 用量与计费：调用量、token 消耗、账单。
- 反馈管理：查看用户反馈、标注数据。
- 报表：效果、成本、活跃度等。


Context 与 Memory 的区别：Context 是当前任务需要的信息，Memory 是过去发生过、以后可能还需要的信息。



> 注意：**RAG 并不是 Agent 的必需四件套之一**，它更像是一种“知识注入/上下文增强”的工程手段，通常在“输入侧增强”阶段发挥作用：先检索外部知识，再把证据拼进 Context，帮助模型减少幻觉并补充时效/私域/长尾知识。它常与记忆、工具、上下文工程配合使用，而不是独立的 Agent 核心部件。

> 这四个组件并非孤立堆叠，而是运行在同一个 **Agentic Loop / Agent 循环**里：感知观察 → 推理决策 → 调用行动 → 拿到反馈 → 再次观察……后文的四种工作模式，都是对这个循环的不同编排。

### 工作模式演进

思考模式的基础：CoT（Chain of Thought，思维链）`Let's think step by step`。

有了上述底层能力后，「如何组织思考与行动」成为关键。业界依次演化出四种典型的工作模式：

#### ReAct 模式

智能体的核心机制是**智能体循环（Agent Loop）**，由感知（Observation）、思考（Thought）和行动（Action）三部分组成。

**感知 (Perception)**：通过传感器（API 监听端口、用户输入接口）接收环境输入。这些观察（Observation）既可以是初始指令，也可以是上一步行动导致的环境状态变化反馈。

**思考 (Thought)**：核心决策阶段，可细分两个环节：
- **规划 (Planning)**：基于观察与内部记忆，更新对任务的理解，制定/调整行动计划，把复杂目标拆成子任务。
- **工具选择 (Tool Selection)**：从工具库中选出最合适的工具并确定调用参数。

**行动 (Action)**：通过执行器（Actuators）执行具体动作（通常为调用工具），对环境施加影响、改变其状态。

环境的 State Change 又产生新的 Observation，被感知捕获后进入下一轮循环，形成持续的"感知-思考-行动-观察"闭环，直至从初始状态推进到目标状态。

```text
Thought: 用户想知道北京的天气。我需要调用天气查询工具。
Action: get_weather("北京")
Observation: 北京当前天气为晴，气温25摄氏度，微风。
```

通过这个由 Thought、Action、Observation 构成的严谨循环，LLM 智能体把内部语言推理能力与外部真实信息和工具操作能力有效结合起来。

#### Plan-and-Execute 模式

ReAct 是「边想边做」，但每步都要完整思考一遍很耗 token。于是出现「三思而后行」的 **Plan-and-Execute**——把「思考」与「行动」彻底解耦，通常由两个不同 LLM 调用或两个阶段协同完成。

- **计划阶段（Plan）**：把复杂目标分解成由多个独立子任务组成的行动清单，子任务相互独立、按逻辑排序。
- **执行阶段（Execute）**：逐一执行每个子任务，"一次只做一步"，并把已完成步骤及结果反馈给模型再继续。
- **校验阶段（Replan，可选）**：执行中若发现环境变化或计划失效，重新规划剩余步骤（Plan-and-Replan）。

相较于 ReAct：优势是单步决策上下文更短、更省 token、减少重复推理；劣势是不做调整时对突发变化不敏感，可能死板执行旧计划。

适用对比：任务逻辑清晰、可离线规划 → Plan-and-Execute；任务需依据中间结果不断调整（如检索型任务）→ ReAct。

#### Reflection 模式

光会执行还不够，让 Agent **学会自我评审再修正**，于是有了 Reflection。

Reflection 是一种赋予智能体「自我批判、自我修正」能力的范式。一个完整反思循环通常包含：

1. **执行**：模型基于当前推理/代码，生成一次尝试输出。
2. **反思 / 评审（Critic）**：用另一角色或同一模型对输出进行批判性审视，找出错误、瓶颈或不合理处，产出 Critique。
3. **修正（Refine）**：模型根据反馈生成优化后的新版本。
4. **迭代**：重复「执行-反思-修正」，直到通过评审或达到迭代上限。

实现常用两个提示词模板配合——反思提示词（如「严格的代码评审专家」）找缺陷，优化提示词（如「资深的程序员」）据此产出改进版。其思想基础是 **Self-Refine** 与 **Self-Critique**，也常与 ReAct 结合（在 Thought 后增加一次自我检查）。

局限性：模型可能"盲目自信"，反思质量受限于自身能力，因此常配合外部验证器（单元测试、规则校验、环境反馈）提供更客观的评判信号。

#### Multi-Agent 模式

单智能体再强也有天花板，于是走向**多智能体分工协作**。核心思想是「三个臭皮匠赛过诸葛亮」：让多个各司其职的 Agent 通过分工、协作与沟通求解复杂任务。主要形态：

- **角色扮演式对话**：如 CAMEL，让两个 Agent（如「程序员」「产品经理」）按约定沟通协议反复对话，协同完成任务。
- **组织化工作流**：如 MetaGPT、CrewAI，模拟分工明确的"虚拟团队"，每个 Agent 有预设职责与 SOP。
- **灵活对话网络**：如 AutoGen、AgentScope，支持自定义 Agent 间的复杂交互拓扑（群聊、嵌套对话、仲裁者等）。
- **主从/编排结构**：一个"老板/编排者"负责任务拆解与验收，多个"工人/专家"并行处理子任务（可参考 Anthropic 的 Multi-Agent Research System）。

多智能体需重点处理三类问题：**通信协议**（谁和谁说什么）、**任务分配与去重**、**结果仲裁与一致收敛**（避免分歧死循环）。代价是更高的 token 成本、更长延迟、更复杂的调试面。

## Harness 工程

提示词工程优化的是「意图的表达」，上下文工程优化的是「信息的供给」，但两者都停留在「输入侧」。当模型真正开始**连续行动**，会出现全新问题：谁来监督它？谁来约束它？谁来在它跑偏时把它拉回来？这就是 Harness 要解决的事——Harness 直译「马具/缰绳」。

关于 Harness 的边界，圈子里流传着一个极简等式：

**Agent = Model + Harness**

翻译成人话：在 Agent 系统里，除了模型本身之外，几乎所有决定它能否稳定交付的东西，都属于 Harness。具体而言，Harness 承载着以下几个环节：

- **循环调度**：把「感知 → 推理决策 → 调用行动 → 获取反馈」组装成受控的 Agent 循环，而不是让模型自由发挥到底。
- **终止与步数约束**：设定步骤上限与明确的 Finish 信号，防止无限推理与无效循环（对应后文「死循环」「过早/过晚收敛」失败模式）。
- **校验与兜底**：对工具调用做 schema 校验、对输出做格式/合法性检查，拦截「幻觉工具调用」。
- **失败自恢复与回溯**：检测级联错误并回滚到先前的安全状态，而不是带病继续。
- **可观测与状态持久化**：记录执行轨迹、耗时、token 用量，并支持断点续跑（对应后文「观测与追踪」「状态管理」）。
- **安全与越权护栏**：约束工具权限、敏感操作白名单，防止模型或提示词注入造成越权行为。

后文的「常见失败模式」与「工程做法」，正是对上述各环节的逐项展开。


## 阶段五：Agent 生态与工程化

### workflow 编排

构造单个 Agent 只是第一步，现实业务往往要把多个能力串成**工作流**，业界沉淀出四种稳定的编排模式：

- **Prompt Chaining（提示链）**：把大任务拆成多个小步骤，前一步输出作为后一步输入，像流水线一样串起来。
- **Routing（路由）**：先用一个 LLM 做分类判断，再按分类结果把请求分发到不同处理分支（客服系统是典型）。
- **Parallelization（并行化）**：把可同时进行的子任务并行执行后汇总，适合多维分析、多源检索等场景。
- **Orchestrator-Workers（编排者-工人）**：一个中央编排者分配任务，多个 Worker 各自完成子任务，适合子任务相互独立的场景。

### 协作模式

多 Agent 之间如何组织，同样演化出几种主流协作模式：

**1. 单智能体自主循环**：早期典型范式（如 AgentGPT），一个通用 Agent 通过"思考-规划-执行-反思"闭环不断自我提示与迭代，完成开放式高层目标。

**2. 多智能体协作**：当前最主流方向，通过模拟人类团队协作来解决复杂问题，又可细分：
- **角色扮演式对话**：如 CAMEL，为两个智能体设定明确角色与沟通协议，在结构化对话中协同。
- **组织化工作流**：如 MetaGPT、CrewAI，模拟分工明确的"虚拟团队"，每个智能体有预设职责与 SOP。
- **灵活对话网络**：AutoGen、AgentScope 允许自定义智能体间的复杂交互网络。

**3. 高级控制流架构**：如 LangGraph，将执行过程建模为**状态图（State Graph）**，灵活实现循环、分支、回溯与人工介入等复杂流程。

### 智能体工程化进阶

当 Agent 从 Demo 走向生产，需要补上框架、评估、安全、可观测性等工程能力。

#### 主流 Agent 框架与开发范式

- **LangGraph**：以状态图为核心，建模节点与边，支持循环、分支、回溯与人工介入（human-in-the-loop），底层工程能力强。
- **CrewAI**：模拟「虚拟团队（Crew）」，用 Role/Goal/Backstory 定义 Agent，通过任务分工协作，上手快。
- **AutoGen**：基于多 Agent 会话，支持「GroupChat」等多智能体拓扑，强调对话驱动。
- **LlamaIndex (Agents)**：以数据/RAG 为中心，提供 ReAct、Function-Calling 等支持，适合知识密集型应用。
- **Metagpt**：软件公司 SOP 的落地实现，将需求→设计→编码→测试标准化到多角色协作。
- 另有 **Semantic Kernel**（微软）、**LlamaCrew**、**Dify/Coze**（低代码）等。选型核心看三点：**控制流复杂度、对人工介入/状态持久化的要求、团队维护成本**。

#### 智能体评估（Agent Evaluation）

评估 Agent 比评估单一模型更难，因为它涉及「过程是否合理」与「结果是否达成」两个维度：

- **评测基准**：SWE-bench（软件工程）、GAIA（通用助手）、AgentBench、tau-bench（面向任务对话）等，用于横向对比。
- **过程指标**：工具调用是否准确、是否在合理步数内收敛、是否死循环、上下文是否溢出。
- **结果指标**：任务完成率（Success Rate）、成本（token 数、调用次数）、延迟（Latency）、可复现性。
- **工程做法**：构建 Golden Dataset + LLM-as-a-Judge 或规则判分器，配合回归测试集，在每次提示词/工具/Harness 变更时重跑评测，防止「改了 A 坏了 B」。

#### 安全与 Guardrails（护栏）

Agent 比普通聊天风险面更大，因为 Agent 会**真实地执行动作**，需要多层护栏：

- **工具权限边界**：区分只读/可写工具，高危操作需人工确认（发邮件、转账、删数据），遵循最小权限原则。
- **输入内容安全**：防 **Prompt Injection（提示注入）**，即外部数据（网页、邮件、工具返回）携带恶意指令劫持 Agent；对外部内容做「内容与指令隔离」。
- **输出行为约束**：拒绝危险指令、限定调用工具范围、设置步骤数/预算上限，防失控循环。
- **审计与留痕**：记录每一步 Thought/Action/Observation 与令牌用量，便于回溯定位。

#### 可观测性与 Agent 生命周期

Agent 的「循环执行」特性决定了它必须具备工程级可观测性：

- **Tracing（链路追踪）**：记录一次任务完整执行轨迹（消息序列、工具调用耗时与结果、token 用量），OpenTelemetry 已定义 `gen_ai` 语义约定，配合 Langfuse、LangSmith、Phoenix 等沉淀"执行日志即数据资产"。
- **状态管理与持久化**：会话不一定在一个请求内结束，需支持执行状态/记忆的持久化、断点续跑（如 LangGraph 的 checkpoint）。
- **流式输出与中间态展示**：实时回流 Thought/Tool 调用中间状态，改善超长任务体验。

#### Agent-to-Agent（A2A）协议

谷歌于 2025 年提出 A2A 协议，用于标准化 **Agent 之间**如何发现彼此、交换能力、传递任务与共享上下文，让不同厂商的 Agent 能互操作。它由 Agent Card（能力宣告）、任务状态机、交互消息等组成，常与 MCP 配合——**MCP 管「Agent→工具/数据」、A2A 管「Agent→Agent」**。

#### 常见失败模式（Failure Modes）

- **死循环 / 无限推理**：步骤数无上限、缺乏终止条件。
- **幻觉工具调用**：调用不存在的工具或传错参数（需工具 schema 校验兜底）。
- **上下文爆炸**：中间产物与观察不断累积导致溢出（需截断/压缩/检索）。
- **过早收敛 / 过晚收敛**：信息不足就下结论，或迟迟不结束（需明确的 Finish 信号）。
- **级联错误**：早期错误观察污染后续决策，难以自愈（需引入验证与回溯）。

好的 Harness 设计 ≈ 针对上述失败模式逐一加「保险丝」。

---

Harness 是把 Prompt、Context、Tools、Memory、Workflow、Guardrails、Evaluation 等东西组织起来，让 Agent 能稳定运行的一层“运行框架/控制层”。
