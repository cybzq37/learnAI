## ReAct 是什么

ReAct 就是构建了一个 感知（Observation）、思考 (Thought)、行动（Action）的智能体循环。

思考：用户输入一个目标？思考阶段大模型进行规划（Plan），有哪几步，需要调用什么工具
行动：负责执行，调用某个工具
观察：执行完之后，对结果进行观察，执行到哪一步，执行成功或者失败，决定下一步做什么，直到目标完成

## ReAct 存在哪些问题

- 迭代效率低：
- 上下文爆炸：每轮都把完整历史塞进prompt，可以上下文压缩 / 关键信息摘要

## ReAct 如何优化

1. Reflexion（反思机制）
在一轮任务结束后，如果任务执行失败，让模型自我反思，“哪里错了、为什么错”，把反思结果作为额外输入重新尝试。

2. Plan-and-Execute（规划-执行分离）
Plan-and-Execute（规划-执行分离） 先让LLM做全局规划（分解成子任务DAG），再按计划逐步执行。好处是避免ReAct的“走一步看一步”导致的局部最优。

## MCP

MCP是一个标准协议，定义了LLM怎么连接外部工具和数据源。

主要包含：Host(Agent)、Client、Server 三种角色

Host就对应我们的智能体，Client 对应 Agent中与Server端进行通信的组件，Server对应了远程的服务。

- Tools（工具）：可执行的函数（如查询天气、发送邮件）
- Resources（资源）：可读取的数据（如文件、数据库记录）
- Prompts（提示模板）：预定义的提示词模板

客户端连接服务端，完成初始化和能力协商；客户端发现工具、资源或提示模板；模型根据任务选择工具；客户端发送结构化调用请求；服务端执行并返回结果；客户端把结果转换成模型可消费的上下文。

它和普通函数调用的差别不只是接口格式。普通函数调用通常是应用内部固定代码之间的调用，而 MCP 更强调跨进程、跨语言、动态发现能力以及统一的上下文接入方式。工程上仍然需要自行解决认证、授权、超时、重试、幂等、审计和结果大小控制。

MCP 工具描述本身也不能直接视为可信内容。工具名称、描述和返回值都需要经过注册审核与权限策略校验。

## 如何设计一个高可靠的MCP Server

MCP Server 不应该把数据库、Shell 或内部 HTTP 接口原样暴露给模型，而应提供粒度明确、参数受限、结果可验证的领域工具。例如不要提供任意 SQL 执行工具，而是提供限定表、限定字段和限定条件的查询接口。

服务端需要具备：

参数 Schema 校验和语义校验。
请求超时、并发限制和熔断。
工具级权限和资源级权限。
敏感字段脱敏与输出大小限制。
幂等键、审计日志和调用链追踪。
稳定的错误码，而不是把堆栈直接返回给模型。
如果服务端涉及流式结果，需要考虑客户端断连后的资源回收、重复消费和最终一致性。对于长任务，可以返回任务句柄，让客户端通过查询或事件订阅获取结果，而不是一直占用同步连接。

## skill 与 function 的区别

function 就是函数调用，功能是比较单一、简单的，比如查询天气、数值计算等。

skill 是一种定义清楚的技能或能力，通过markdown描述，（能力的具体描述？有哪些步骤？调用什么工具？输出什么格式？），能执行复合操作，可以包含多轮对话、上下文记忆、步骤流转（如先查票，再选座，最后支付）。

## langchain 和 langgraph 面试相关

langchain相当于大模型的基础设施工具箱，封装了很多的工具，比如大模型的调用、管理对话历史、调用工具等，不需要自己实现了，能够直接使用；LangGraph是基于langchain的，基于图结构流构建，原生支持分支、循环、并行等复杂流程逻辑，能够支持状态管理、复杂的流程管控、多智能体协作等。

LangChain的核心组件是Model、PromptTemplate、Chain、StrOutputParser、Agent、Memory。其中，Chain是固定执行流程，数据按预设路径流动；而Agent是动态决策者，LLM自主判断下一步调用哪个工具，更灵活但更难控制。

- Memory：主要包括存储（Save）保存会话 和 提取（Load）提取会话。

全量记忆：`InMemoryChatMessageHistory` 完整保存所有对话历史，适用于短对话场景
窗口记忆：截取 `InMemoryChatMessageHistory`，仅保留最近N轮对话，控制Token消耗
摘要记忆：通过LLM生成对话摘要替代完整历史，平衡上下文连贯性与效率

- 工具调用  `@tool`注解注册工具

- 路由链 

RunnableBranch 根据输入内容或条件进行判断，将请求动态分发到不同处理分支
RunnableSequence 多个组件按固定顺序执行，前一个组件的输出作为后一个组件的输入；支持 | 运算符或 from_chain() 创建，提供 .invoke() / .stream() / .batch() 方法，可搭配 RunnablePassthrough 实现多输入传递
RunnableRetry、RunnableWithFallback

langgraph核心组件：

- State（状态）：共享数据载体 + 状态快照，用于传递和存储中间结果（比如第一步的原始建议、第二步的精简建议）；
- Node（节点）：每个节点对应一个函数，负责完成一个具体任务（生成建议、精简建议），函数接收状态作为输入，处理后返回更新后的状态；
- Edge（边）：定义节点的执行顺序（START → generate → simplify → END），相当于工作流的“流程规划图”；
- compile（编译）：把状态图、节点、边的定义，转换成可执行的工作流实例；
- invoke（执行）：传入初始状态，工作流会按定义的顺序执行节点，最终返回完整的状态（包含所有中间结果和最终结果）。

graph_builder = StateGraph(TextProcessState) `add_node` `add_edge` `add_conditional_edges`

LCEL是一种声明式语法，使用|管道符组合组件（如retriever | prompt | llm）。它的核心优势是简洁、原生支持流式(stream)和批处理(batch)，且所有组合后的Runnable都共享同一套接口，代码更优雅、生产性更强。

## 如何处理Memory（记忆）与上下文窗口的长度冲突？

LangChain提供了多种Memory策略应对此问题：

- ConversationBufferWindowMemory：滑动窗口，只保留最近K轮对话，简单直接。

- ConversationSummaryMemory：用LLM将长历史压缩为摘要，保留关键信息但增加了成本。

- VectorStoreRetrieverMemory：将历史存入向量库，按需检索相关记忆，适合长期记忆场景。

## 上下文管理

上下文的七大组成要素：

- System Instructions — 系统指令，定义角色和行为边界
- User Prompt — 用户的当前请求
- Conversation History — 对话历史
- Long-Term Memory — 跨会话的长期记忆
- Retrieved Information (RAG) — 实时检索的外部知识
- Available Tools — 可用工具的定义和 schema
- Output Format — 输出格式要求

## 长上下文如何压缩

保留最近3次的会话信息，然后对历史会话进行摘要压缩，保存结构化的信息：

{
  "goal": "分析某批次数据中的异常变化",
  "constraints": ["不能访问生产库", "结果需要给出置信区间"],
  "confirmed_facts": ["样本量为 1200", "缺失率为 2.1%"],
  "decisions": ["使用隔离沙箱运行 Python"],
  "open_questions": ["异常是否与设备批次有关"],
  "artifacts": ["artifact://analysis/result-v3.csv"]
}

记录这次压缩的会话返回，下次压缩的时候，从当前位置继续压缩。

## 多 Agent 协作，如何解决 Agent 之间的循环调用和责任不清

应该明确每个 Agent 的角色，保持单一职能，明确输入和输出，都要定义成结构化的参数。

设计好全局状态，每个Agent执行完成之后都要返回当前状态，保证整个图严格按照状态图走。

## 如何设计 Agent 的任务状态机，使长任务支持暂停、恢复和重试

任务状态、步骤状态和执行产物需要分离。任务整体状态表示用户任务是否完成；步骤状态表示某个节点是否执行成功；产物则保存具体的代码、日志、数据和模型响应。

每次状态变化都要持久化事件，例如 StepStarted、ToolCalled、ToolFinished、StepFailed。恢复时从最后一个一致性检查点继续，而不是重新让模型回忆全过程。

重试也要区分错误类型：网络超时可以重试，参数错误需要修正后重试，权限错误不应该盲目重试，业务结果不符合约束则应进入验证失败流程。对于副作用操作，例如提交实验、写入数据库，必须使用幂等键或事务机制，防止恢复时重复执行。

## RAG 索引流程

数据加载（Loading）：
- 能够解析不同格式的文档，将 PDF、WORD、Markdown等内容提取为可处理的文本（Unstructured、MarkItDown库）
- 在解析文档的同时，提取文档版本、作者、时间等元数据信息
- 整理成统一的结构化数据，方便后续 切分、向量化、入库

文本分块（Chunking）：
- Unstructured文档结构分块
- 递归字符分块
- 语义分块（句子分割、上下文感知嵌入、识别断点、合并成块）

> 如何解决语义跳跃的问题？
> 计算所有差异值的平均值和标准差。当一个差异值超过“平均值 + N * 标准差”时，被视为异常高的跳跃，即断点。

同时要给Chunking添加元信息，页码、章节、标题等信息。

索引构建：
把chunking转为向量，和元数据信息一起存入向量数据库，同时建立ANN索引（HNSW、DiskANN）

## RAG 检索流程

```
用户问题
   ↓
问题理解 / Query Rewrite
   ↓
检索（Retrieval）
   ↓
召回相关文档
   ↓
Rerank 重排序
   ↓
构造 Prompt + 上下文
   ↓
LLM 生成答案
   ↓
返回答案
```

```
用户问题
   ↓
Query 理解 / 改写
   ↓
Query Embedding
   ↓
向量数据库检索
   ↓
召回 Top-K 文档
   ↓
重排序 Rerank
   ↓
上下文组装 Context
   ↓
Prompt + Context
   ↓
LLM 生成答案
   ↓
引用 / 结果后处理
```

*Query Rewrite 如何处理？*

1. 处理口语、缩写、错别字、同义词。  
2. 补充上下文。  
3. 多个Query扩展（用户使用的是一个词，但知识库可能使用另外的术语。）
4. HyDE 假设性文档生成（属于比较特殊的一类）

*RAG 召回优化有哪些？*

先进行检索前过滤，Metadata Filtering，现根据标量缩小查询范围。然后进行向量检索：

1. 多路召回（Multi-path Retrieval） 不只用向量检索、同时用BM25关键词检索、图检索等，多路结果合并、去重、排序并返回。
2. 混合检索（Hybrid Search） 向量相似度 + 关键词匹配，**加权融合**。
3. 重排序（Rerank） 先用快方法召回Top-100，再用Cross-Encoder重新打分，取Top-5。

*RAG rerank优化有哪些？*

1. 使用 RRF (倒数排名融合)融合多路召回数据，不看具体分数，只看文档在不同召回方式中的排名位置，通过公式 1/(k+排名) 融合多个排名列表。
2. Cross-Encoder (交叉编码器) 将查询和每个文档拼接成一个整体输入模型，让模型进行深度语义交互和注意力计算，直接输出一个相关性分数。


*RAG检索慢的优化思路*

1. query rewrite慢，靠能导致1秒的耗时
2. 多路或混合召回，控制召回的数量
3. rerank耗时，主要是计算分数耗时
4. 增加缓存 Embedding Cache、Retrieval Cache、Rerank Cache、LLM Response Cache



## KV Cache 是什么，如何提升命中率

大模型的自注意力机制，每个 Token 会产生 Q/K/V 三个参数。Q 表示 我想找什么？ K 表示 我这里有什么信息？ V 表示 真正要提供的信息是什么？

KV Cache 只缓存 K 和 V，而不缓存 Q：生成下一个 Token 时，Q 是当前这个新 Token 临时产生的查询，而历史 Token 的 K/V 可以直接复用。

KV Cache的时间是由大模型的缓存策略决定的。

提高命中率的方法？

请求的结构化信息尽量稳定。

```
[稳定内容]
System Prompt
Tool Definitions
User Profile
Long-term Memory

[动态内容]
Current Time
Current User Query
```

为了提高上下文命中率，可以采用下面的上下文组织方式：

```
┌─────────────────────────────┐
│ ① System Prompt             │ ← 极稳定
├─────────────────────────────┤
│ ② Tool Definitions          │ ← 稳定
├─────────────────────────────┤
│ ③ Developer / Policy        │ ← 稳定
├─────────────────────────────┤
│ ④ User Profile              │ ← 低频变化
├─────────────────────────────┤
│ ⑤ Long-term Memory          │ ← 中低频变化
├─────────────────────────────┤
│ ⑥ Stable Conversation       │ ← 相对稳定
├─────────────────────────────┤
│ ⑦ Dynamic Context           │ ← 高频变化
│    - 当前时间               │
│    - 当前状态               │
│    - 当前工具结果           │
│    - 当前问题               │
└─────────────────────────────┘
```

## 沙箱执行环境应该重点防范哪些风险

至少要防范任意代码执行、资源耗尽、敏感信息读取、网络外传、恶意依赖安装、进程逃逸和跨任务数据泄露。推荐将代码运行放在一次性隔离环境中，使用非特权用户、只读基础镜像、临时工作目录、CPU/内存/磁盘/进程数限制和默认断网策略。

文件访问采用白名单，密钥不注入沙箱；如果必须访问外部服务，应通过受控代理并限制域名、方法、请求体和返回大小。执行结束后销毁环境，产物通过扫描后上传到隔离存储。

```
docker run --rm \
  --network=none \
  --read-only \
  --cap-drop=ALL \
  --pids-limit=64 \
  --memory=512m \
  --cpus=1 \
  --user=1000:1000 \
  agent-sandbox:latest python /workspace/main.py
```

容器隔离并不等于绝对安全，生产环境还应结合更强的微虚拟机、系统调用限制和宿主机监控。

## 如何设计 Agent 的可观测性和线上问题定位体系

一次用户请求需要贯穿完整 Trace，至少记录请求 ID、用户 ID、任务 ID、模型版本、提示词版本、工具名称、参数摘要、Token、耗时、重试次数、错误码和最终状态。敏感内容不能直接写入日志，应进行脱敏或哈希化。

指标可以分为四层：系统层的 QPS、延迟和错误率；模型层的 Token、模型失败率和结构化输出通过率；工具层的超时、权限拒绝和返回错误；业务层的任务成功率、人工接管率和结果采纳率。

出现“任务成功率下降”时，不能只看模型日志，还要按模型版本、提示词版本、工具版本、用户类型和任务类型进行切分。最好保存可回放的输入摘要和中间状态，使问题能够在脱离生产数据的环境中复现。
