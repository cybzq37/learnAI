# Kafka 面试题

### 消息队列的作用

系统解耦、缓冲请求（削峰填谷）、异步处理、广播通知。

### 消费重复如何解决？

生产端为了保证消息发送成功，可能会重复推送(直到收到成功ACK)，会产生重复消息。所以，只能业务端自己做控制，对于已经消费成功的消息，本地数据库表或Redis缓存业务标识，每次处理前先进行校验，保证幂等（消费幂等）。

### 消息丢失如何解决？

- 消息生产阶段：生产者会不会丢消息，取决于生产者对于异常情况的处理是否合理。从消息被生产出来，然后提交给 MQ 的过程中，只要能正常收到 （ MQ 中间件） 的 ack 确认响应，就表示发送成功，所以只要处理好返回值和异常，如果返回异常则进行消息重发，那么这个阶段是不会出现消息丢失的。
- 消息存储阶段：Kafka 在使用时是部署一个集群，生产者在发布消息时，队列中间件通常会写「多个节点」，也就是有多个副本，这样一来，即便其中一个节点挂了，也能保证集群的数据不丢失。
- 消息消费阶段：消费者接收消息+消息处理之后，才回复 ack 的话，那么消息阶段的消息不会丢失。不能收到消息就回 ack，否则可能消息处理中途挂掉了，消息就丢失了。

### Kafka 架构（核心概念）

- Broker：消息中间件处理结点，一个Kafka节点就是一个broker，多个broker可以组成一个Kafka集群。
- Topic：一类消息，Kafka集群能够同时负责多个topic的分发。
- Partition：topic 物理上的分组，一个topic 可以分为多个 partition，每个partition是一个有序的队列。
- Segment：partition 物理上由多个segment组成。
- offset：每个 partition 都由一系列有序的、不可变的消息组成，这些消息被连续的追加到 partition 中。partition中的每个消息都有一个连续的序列号叫做offset, 用于partition唯一标识一条消息。
- **Producer**：生产者，按分区策略发送消息；
- **Consumer / Consumer Group**：组内成员**分摊**消费不同分区（一个分区同一时刻只能被组内一个消费者消费）；
- 元数据与 Leader 选举：老版本依赖 ZooKeeper，新版本（KRaft）已去 ZK。

### Topic Partition 物理存储结构（高价值）

每个 Partition 在磁盘上对应一个**目录**（`<topic>-<分区号>`），目录内按 offset 顺序切成多个 **Segment 文件组**：

```text
kafka-logs/                      # log.dirs 配置的根目录
├── order-topic-0/               # 分区目录：命名 = <topic>-<分区号>
│   ├── 00000000000000000000.log        # 消息数据文件（第一个 segment，从 offset 0 开始）
│   ├── 00000000000000000000.index      # 偏移量索引（稀疏索引）
│   ├── 00000000000000000000.timeindex  # 时间索引（按时间戳定位消息）
│   ├── 00000000000000120960.log        # 第二个 segment，从 offset 120960 开始
│   ├── 00000000000000120960.index
│   └── 00000000000000120960.timeindex
├── order-topic-1/
└── order-topic-2/
```

关键要点：

- **目录命名**：`<topic>-<partition>`（如 `order-topic-0`），**副本不单独建目录**，Follower 只在自己所在的 broker 上同步同一份数据；
- **Segment 命名**：文件名 = 该 segment **第一条消息的 offset**，用 **20 位十进制**补齐（`00000000000000000000.log`）；
- **滚动规则**：segment 达到 `log.segment.bytes`（默认 **1GB**）或超过 `log.roll.hours`（默认 7 天）自动滚动，生成新的 segment；
- **写入**：消息只追加到**最后一个 segment** 的 `.log` 文件尾部，这就是"顺序写磁盘"，也是 Kafka 快的重要原因之一；
- **查找流程**：按 offset 二分定位到 segment → 查 `.index`（**稀疏索引**，不是每条消息都建，默认每 4KB 记录一条 offset→物理位置映射）→ 在 `.log` 内顺序扫描找到消息，兼顾内存占用与查询速度；
- **日志清理**：超过 `log.retention.hours`（默认 168h）的**过期 segment 整体删除**（delete 策略）；或按 key 做 **compact**（日志压缩，每个 key 只保留最新一条，适合存"最新状态"类数据）；
- 索引文件通过 **mmap** 内存映射加载，查询时几乎不产生磁盘 IO。

### 集群下 Partition / Replica 分配规则（高价值）

创建 Topic 时由 **Controller** 执行分配算法，核心目标：**分区、副本、Leader 在集群内尽量均匀，且同一分区的副本不落在同一台 broker**（否则该 broker 宕机时该分区所有副本一起丢失）。

**默认分配算法（未开启机架感知）**：

1. **副本跨 broker**：同一分区的多个副本必须分布在**不同 broker** 上；
2. **Leader 轮询分布**：分区按序号依次分配 Leader，Leader 位置在 broker 列表上轮询（`(startIndex + partitionId) % brokerCount`），保证每个 broker 上的 Leader 数大致相等；
3. **Follower 向后顺延**：每个分区的第 2、3…个副本从前一个副本位置**向后顺延**选取（跳过已选的 broker），使副本分布均匀错开。

```text
例：3 个 broker（B0/B1/B2），创建 3 分区、2 副本的 topic：

分区 0 → Leader: B0，副本: [B0, B1]
分区 1 → Leader: B1，副本: [B1, B2]
分区 2 → Leader: B2，副本: [B2, B0]

结果：每个 broker 上恰好 1 个 Leader + 1 个 Follower，完全均衡
```

其他要点：

- **机架感知（rack-aware）**：配置 `broker.rack` 后，算法优先把同一分区的副本分配到**不同机架**（副本数 ≤ 机架数时保证跨机架），防止整机架断电/交换机故障导致数据不可用；
- **Leader 选举**：Leader 负责读写，Follower 只从 Leader 拉取同步；Leader 宕机后，从 **ISR**（同步中的副本集合）里选新 Leader，**不会选落后过多的 OSR 副本**（防止丢消息）；`auto.leader.rebalance.enable` 会周期性把 Leader 重新均衡到各 broker；
- **新增 broker 不会自动迁移分区**：需要手动执行 `kafka-reassign-partitions.sh` 做分区重分配，迁移期间可用 `replica.fetch.max.bytes` 限速控制流量，避免影响线上。

### 消息顺序性如何保证

- **单分区内有序**：Kafka 只保证同一分区内消息有序。
- 需要全局有序：只用一个分区（牺牲吞吐）；或按业务 key 指定分区（如订单号 hash 到同一分区，保证同一订单的消息有序）。

### Kafka 为什么快（高价值）

1. **顺序写磁盘**：消息追加写入文件末尾，顺序写性能接近内存；
2. **页缓存（Page Cache）**：读写利用操作系统页缓存，不经过 JVM 堆；
3. **零拷贝（Zero Copy）**：消费时用 sendfile，数据从内核直接发到网卡，避免用户态/内核态拷贝；
4. **批量与压缩**：批量发送/拉取，支持 lz4、zstd 等压缩；
5. **分区并行**：分区越多并行度越高。

### 消息积压如何解决

1. 定位消费慢的原因（消费逻辑耗时、DB 慢、单分区无并行）；
2. **扩容消费者**：增加消费者实例，但**分区数必须 ≥ 消费者数**，否则加了也白加；
3. 临时方案：新起一个多分区 Topic，把积压消息快速转存后并行消费；
4. 优化消费逻辑：批量处理、异步化、减少 RPC 调用。

### Kafka 与 RabbitMQ 的区别

| 对比项 | Kafka | RabbitMQ |
|---|---|---|
| 定位 | 分布式流处理平台，高吞吐 | 传统消息队列，功能丰富 |
| 吞吐量 | 百万级/秒 | 万级/秒 |
| 消息有序 | 分区内有序 | 单队列内有序 |
| 堆积能力 | 基于磁盘，堆积能力强 | 堆积能力弱 |
| 可靠性 | ISR / ack 配置保证 | confirm、事务等机制完善 |
| 典型场景 | 日志、埋点、大数据流 | 业务消息、异步任务 |

### 消费者组与 Rebalance

消费者加入/退出、分区数变化时触发 **Rebalance（重平衡）** 重新分配分区。Rebalance 期间整个消费者组**停止消费**，所以不要频繁启停消费者，分区数要提前规划好。

### ISR 机制与 ack 参数

- **ISR（In-Sync Replicas）**：与 Leader 保持同步的副本集合。消息先写 Leader，Follower 从 Leader 拉取同步，跟不上进度的被踢出 ISR。
- **ack 参数**：`acks=0`（不等确认，可能丢）、`acks=1`（Leader 写入成功即确认，默认）、`acks=all/-1`（ISR 全部写入成功才确认，最安全）。
