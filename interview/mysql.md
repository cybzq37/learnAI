# MySQL 面试题

### 索引为什么用 B+ 树（高价值）

1. **B+ 树矮胖**：非叶子节点只存键不存数据，单节点能存更多索引项，3~4 层支撑千万级数据，**磁盘 IO 次数少**；
2. **叶子节点有序且链表串联**：天然支持**范围查询**和排序；
3. 数据都在叶子节点，查询次数稳定；
4. 对比：B 树节点存数据（树更高、范围查询弱）、红黑树（太高，IO 多）、Hash 索引（不支持范围查询）。

### 聚簇索引与非聚簇索引

- **聚簇索引（主键索引）**：叶子节点直接存**整行数据**，一张表只能有一个，InnoDB 中"数据即索引"；
- **非聚簇索引（二级索引）**：叶子节点存**主键值**，查询需"**回表**"（先查二级索引拿主键，再回聚簇索引查数据）；
- **覆盖索引**：查询列都包含在二级索引中，无需回表，性能最好。

### 最左前缀原则与索引失效场景

- **最左前缀**：联合索引 (a, b, c) 可命中 a、a,b、a,b,c，条件必须从最左列开始。
- **索引失效场景（必背）**：① 对索引列**使用函数或运算**（`where YEAR(time)=2024`）；② **隐式类型转换**（字符串列没加引号）；③ 前导模糊查询 `like '%xx'`；④ `or` 连接非索引列；⑤ 联合索引不满足最左前缀；⑥ `!=` / `not in` 可能失效（由优化器决定）。

### 事务四大特性（ACID）

- **原子性（Atomicity）**：要么全成功要么全回滚 → 由 **undo log** 保证；
- **一致性（Consistency）**：事务前后数据完整性不被破坏 → 代码约束 + 其他三性共同保证；
- **隔离性（Isolation）**：并发事务互不干扰 → 由**锁 + MVCC** 保证；
- **持久性（Durability）**：提交后数据不丢失 → 由 **redo log** 保证。

### 隔离级别（必背）

| 隔离级别 | 脏读 | 不可重复读 | 幻读 |
|---|---|---|---|
| 读未提交（Read Uncommitted） | 可能 | 可能 | 可能 |
| 读已提交（Read Committed） | 避免 | 可能 | 可能 |
| 可重复读（Repeatable Read，MySQL 默认） | 避免 | 避免 | 基本避免（间隙锁解决） |
| 串行化（Serializable） | 避免 | 避免 | 避免 |

MySQL 默认 **RR**（Oracle 默认 RC）。RR 下 InnoDB 通过 **MVCC（快照读）+ 间隙锁/临键锁（当前读）** 解决幻读。

### MVCC 原理

多版本并发控制：每行记录有隐藏列（事务 id、回滚指针），**undo log 形成版本链**，通过 **ReadView（快照）** 判断对哪个版本可见。
- **RC**：每次 select 生成新 ReadView → 能看到已提交的新数据（不可重复读）；
- **RR**：事务内第一个 select 生成 ReadView 后**复用**（快照固定 → 可重复读）；
- 快照读不加锁（靠版本链），当前读（`select ... for update` / update / delete）加锁。

### InnoDB 锁机制

- 按粒度：**表锁**、**行锁**（InnoDB 特有，基于索引实现，锁的是索引记录）；
- 行锁三类：**记录锁（Record Lock）**、**间隙锁（Gap Lock，锁区间防插入）**、**临键锁（Next-Key Lock = 记录锁 + 间隙锁，RR 默认，防幻读）**；
- **意向锁**：表锁与行锁的协调标记，避免判断冲突时全表扫描；
- 注意：**行锁必须命中索引**，否则退化为表锁。

### 死锁的产生与解决

两个事务互相持有对方需要的锁且互不相让。解决：① InnoDB 自动检测并回滚**代价较小**的事务（`show engine innodb status` 查看）；② 加锁顺序保持一致；③ 尽量缩短事务、减少锁范围；④ 合理使用索引减少锁行数。

### binlog / redo log / undo log（高价值）

| 日志 | 归属 | 作用 |
|---|---|---|
| **redo log**（重做日志） | InnoDB | 崩溃恢复，保证**持久性**；WAL 先写日志再写数据 |
| **undo log**（回滚日志） | InnoDB | 事务回滚 + MVCC 版本链，保证**原子性** |
| **binlog**（二进制日志） | MySQL Server 层 | 主从复制 + 数据恢复 + Canal 数据同步 |

两阶段提交（2PC）：事务提交时 binlog 和 redo log 都写入成功才算提交成功，保证两份日志一致。

### 主从复制

- 原理：主库写 **binlog** → 从库 IO 线程拉取写入**中继日志（relay log）** → 从库 SQL 线程重放；
- 模式：异步复制（默认）、半同步复制、组复制；
- 主从延迟解决：① 实时性要求高的走主库；② 半同步复制；③ 并行复制（从库多线程重放）；④ 分库分表降低单库压力。

### 分库分表

- **垂直拆分**：按业务模块拆库、按字段拆表（大字段单独成表）；
- **水平拆分**：按某个字段（如用户 id）取模 / 范围 / 一致性哈希分到多张表；
- **带来的问题**：分布式事务（Seata/TCC）、跨库 join（冗余字段/应用层组装）、分布式 ID（雪花算法）、排序分页（各分片查再合并）；
- **什么时候做**：单表千万级、写瓶颈明显时考虑，不要过早分库分表（先优化索引和缓存）。

### SQL 优化与 explain

- 慢查询定位：开启慢查询日志 `slow_query_log`，或 `EXPLAIN` 分析执行计划；
- explain 关键字段：**type**（all < index < range < ref < eq_ref < const，从左到右性能变好）、**key**（实际用的索引）、**rows**（扫描行数）、**Extra**（出现 Using filesort / Using temporary 要优化）；
- 优化手段：① 为 where / order by / group by 建合适索引；② 避免 `select *`，用覆盖索引；③ 大分页用**延迟关联**（先查 id 再回表）；④ 避免在索引列上做函数运算；⑤ 大事务分批 delete/update。
